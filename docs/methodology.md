# Методика оценки ML-матчинга «товар → виды работ»

Полный отчёт с цифрами по каждому виду работ, абляцией и примерами ошибок: [reports/metrics_synthetic.md](../reports/metrics_synthetic.md).
Воспроизведение: `make data train eval` (данные генерируются детерминированно, seed 42; эмбеддинги кэшируются).

## 1. Постановка

- **Задача:** многометочная классификация. Каждому товару присваивается множество видов работ из
  [справочника](taxonomy.md) (26 классов); пустое множество означает «не относится к ремонту помещений».
- **Вход:** карточка в формате API стенда: название, путь в дереве категорий, описание, маркетинговое описание,
  характеристики `characteristics` / `propertiesBottom`.
- **Выход:** набор видов работ, вероятность по каждому виду (для ранжирования), класс материала, подходящие помещения.

## 2. Данные

| Набор | Объём | Назначение |
|---|---|---|
| `data/catalog/products.json` + `data/gold/labels.csv` | 1 140 товаров, 124 подтипа | обучение и кросс-валидация |
| `data/catalog/new_products.json` + `data/gold/labels_new.csv` | 155 товаров | отдельная проверка на новых товарах (в обучении не участвуют) |
| `data/gold/review_sample.csv` | 248 товаров (по 2 из каждого подтипа) | независимая ручная перепроверка двумя участниками |

Состав каталога: 265 товаров (23%) относятся к нескольким видам работ, 82 товара (7%) — вне ремонта
(сад, быт, СИЗ, кладка, фасад). Специально добавлены неоднозначные товары: грунтовка (6 видов работ),
монтажная пена, обои под покраску, клей для стеклохолста, полотенцесушитель, универсальный инструмент.
В карточках есть шум, как в реальном каталоге: у 18% товаров пропущены характеристики, у части нет описания,
встречаются артикулы в названии и бренд в верхнем регистре.

**Эталон.** Разметка выполнена по правилам R1–R7 справочника на уровне подтипа товара. Чтобы метрики не
опирались только на нашу собственную разметку, образец из 248 товаров независимо размечают два участника
команды (`python -m scripts.review_sample`), затем считается каппа Коэна по каждому виду работ и расхождения
разбираются с уточнением правил (`python -m eval.agreement`).

## 3. Протоколы

| Протокол | Как устроен | Что проверяет |
|---|---|---|
| **5-fold по товарам** | KFold(5, shuffle, seed 42) | качество на знакомых типах товаров, основной сценарий: новые SKU существующих видов |
| **5-fold по подтипам** | GroupKFold(5) по подтипу: в тесте только виды товаров, которых модель не видела | обобщение «по смыслу», а не запоминание шаблонов; холодный старт новых видов товаров |
| **Новые товары** | обучение на всём каталоге, тест на отдельной выгрузке | воспроизводимость на новых данных, как при загрузке со стенда |

Пороги классификатора подбираются только на out-of-fold предсказаниях **внутри обучающей части**
(вложенная 3-fold кросс-валидация), поэтому тестовые товары не участвуют ни в обучении, ни в подборе порогов.

## 4. Метрики

| Метрика | Что показывает | Цель |
|---|---|---|
| **micro-F1** (основная) | качество по всем парам «товар — вид работ» | ≥ 0,8 |
| macro-F1 | качество на редких видах работ (каждый вид с равным весом) | — |
| samples-F1, exact match | качество набора меток у отдельного товара | — |
| nDCG@10, MAP | качество ранжирования товаров внутри каждого вида работ (то, что видит пользователь в подборе) | — |
| доля верных ответов «вне ремонта» | модель не навязывает виды работ лопатам и мангалам | — |
| multi-label micro-F1 | качество на товарах с ≥ 2 видами работ | — |
| accuracy класса материала | корректность выбора формулы расхода | — |

## 5. Результаты

| Модель | Протокол | micro-F1 | macro-F1 | nDCG@10 | MAP | вне ремонта | multi-label F1 |
|---|---|---|---|---|---|---|---|
| baseline (TF-IDF + LR) | по товарам | 0,991 | 0,991 | 1,000 | 0,999 | 0,988 | 0,987 |
| baseline | новые товары | 1,000 | 1,000 | 1,000 | 1,000 | 1,000 | 1,000 |
| baseline | **незнакомые подтипы** | 0,519 | 0,400 | 0,517 | 0,467 | 0,939 | 0,342 |
| **hybrid** | по товарам | **0,970** | 0,969 | 1,000 | 0,995 | 0,951 | 0,956 |
| **hybrid** | новые товары | **0,988** | 0,984 | 0,999 | 0,996 | 1,000 | 0,986 |
| **hybrid** | **незнакомые подтипы** | **0,676** | 0,620 | 0,812 | 0,694 | 0,720 | 0,454 |

**Абляция гибрида на незнакомых подтипах:** без zero-shot компонента micro-F1 0,575, nDCG@10 0,630, то есть
zero-shot сопоставление со справочником даёт основной прирост. Без kNN micro-F1 почти не меняется (0,685),
но ранжирование хуже (nDCG@10 0,790 против 0,812).

**Производительность** (Apple M1 Pro, 16 ГБ): обучение 15 с, инференс 0,36 мс на товар (+ эмбеддинги),
эмбеддинги всего каталога 13 с без кэша, пиковая память процесса оценки ≈ 1,1 ГБ, полная оценка ≈ 6 минут.
Сервис размечает 155 товаров со стенда вместе с загрузкой примерно за 0,7 с.

## 6. Интерпретация и ограничения

1. **Цель micro-F1 ≥ 0,8 достигнута** на протоколах по товарам и на новых товарах. Это основной
   производственный сценарий: в каталог приходят новые SKU уже известных видов товаров.
2. **Цифры на знакомых типах завышены синтетикой.** Названия и описания генерируются из шаблонов, поэтому
   простая модель «запоминает» подтипы (baseline 0,99). Реальный каталог разнообразнее, и цифры на нём будут ниже.
   Поэтому мы отдельно считаем самый жёсткий протокол, незнакомые подтипы, и улучшаем модель именно на нём.
3. **Почему гибрид на знакомых типах чуть ниже baseline** (0,970 против 0,991). Zero-shot компонент сглаживает
   уверенные предсказания логрегрессии ради обобщения. Мы сознательно выбрали веса, которые дают
   +16 п.п. micro-F1 и +30 п.п. nDCG@10 на незнакомых видах товаров ценой −2 п.п. на знакомых.
4. **Слабые места** (незнакомые подтипы): классы, которые в каталоге представлены одним-двумя видами товаров
   (вентиляция, двери, подоконники, линолеум). Шлюз «вне ремонта» на незнакомых подтипах ошибается чаще (0,72).
   План: локальная LLM (Ollama) для товаров с низкой уверенностью, расширение описаний видов работ в справочнике,
   дообучение на реальной размеченной выборке.

## 7. Предложение по независимой проверке

1. Заказчик передаёт размеченную выборку: карточки в формате API стенда и CSV `id;work_types` с кодами
   из справочника через «|». Если у заказчика своя таксономия — передаётся таблица соответствия.
2. Мы запускаем `python -m eval.evaluate` с путями к этим файлам: протокол «новые товары», модель обучена на
   нашем каталоге. Отчёт формируется автоматически.
3. Дополнительно, если заказчик готов: дообучение на части выборки и проверка на оставшейся.
